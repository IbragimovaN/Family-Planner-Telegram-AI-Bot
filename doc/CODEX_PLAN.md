# Family Planner — план реализации для Codex

Этот файл используется вместе с `SPEC.md`. Выполнять этапы строго по порядку. После каждого этапа — проверка и отдельный коммит. Развёртывание выполняется только после успешных локальных проверок в следующих точках:

- после этапа 3: совместный релиз этапов 1–3 — SQLite, полная авторизация, семьи, участники, приглашения и настройки семьи;
- после этапа 4: мобильный каркас;
- после каждого из этапов 5–9: покупки, ежедневные дела, неделя и месяц, вишлисты, уведомления;
- после этапа 10: итоговое обновление и приёмка MVP по этапу 11.

После этапов 0, 1 и 2 отдельного развёртывания нет. Для каждого релиза используется порядок из этапа 11; проверяются только уже реализованные функции. Критические проверки авторизации, изоляции семей, валидации и сохранности данных выполняются перед первым релизом и расширяются с каждой функцией, а не откладываются целиком до этапа 10.

## Общие правила для Codex

Перед каждым этапом:

1. Прочитать `SPEC.md`, `README.md`, `package.json`, `server/package.json`, Docker-файлы и относящийся к этапу код.
2. Не удалять работающий функционал без явной необходимости.
3. Не менять одновременно архитектуру, дизайн и бизнес-логику за пределами этапа.
4. Сначала описать короткий план и список изменяемых файлов.
5. Использовать TypeScript без необоснованных `any`.
6. Добавлять валидацию входных данных и обработку ошибок.
7. Не помещать секреты и персональные данные в код, Git или логи.
8. После изменений выполнить доступные lint, typecheck, tests и build.
9. Если существующий код противоречит спецификации, остановиться и явно описать конфликт.
10. В конце дать команды проверки и краткий результат.

## Этап 1. Основа базы данных SQLite

Статус: выполнен 30 сентября 2026. Новая пустая БД создана после резервного копирования старой; 9 тестов, lint, обе сборки и проверка сохранности данных при перезапуске Docker прошли. Команды и результаты: `docs/DATABASE.md`. Развёртывание на VPS не выполнялось.

### Задача

Добавить SQLite и систему миграций, не реализуя пока весь новый интерфейс.

### Требования

- выбрать одну поддерживаемую SQLite-библиотеку, совместимую с текущей версией Node;
- создать миграции для таблиц из `SPEC.md`;
- добавить foreign keys и необходимые индексы;
- путь к БД задавать через `DATABASE_PATH`;
- в Docker хранить файл БД в существующем постоянном volume;
- не выполнять destructive schema sync при запуске;
- добавить безопасную команду миграции;
- по результатам этапа 0 хранилище уже SQLite (`better-sqlite3`), а не JSON;
- решение пользователя: начать с пустой БД без импорта старых задач; перед переходом создать согласованную резервную копию существующей SQLite-базы с учётом WAL;
- новую схему создавать версионированными миграциями на пустой БД; очистка не должна повторяться при обычном запуске или повторном выполнении миграций.

### Проверка

- миграции работают на пустой базе;
- повторный запуск миграций ничего не ломает;
- контейнер перезапускается без потери данных;
- database-файл не попадает в Git.

## Этап 2. Telegram-авторизация

Статус: реализован 30 сентября 2026. Проверки подписи, сессий, logout, запрета dev-режима в production и браузерный сценарий локального входа пройдены. Инструкция самостоятельной проверки: `docs/AUTH_CHECK.md`. Реальный вход из Telegram требует токена бота и HTTPS-стенда; проверка запланирована после размещения версии, VPS на этом этапе не обновлялся.

### Задача

Реализовать серверную проверку Telegram Mini App `initData` и защищённую сессию.

### Требования

- frontend получает исходный `Telegram.WebApp.initData`;
- `POST /api/auth/telegram` проверяет подпись и `auth_date`;
- создать или обновить пользователя по Telegram ID;
- создать HttpOnly-сессию;
- добавить `GET /api/me` и logout;
- все будущие `/api` endpoint, кроме health и auth, защищать middleware;
- вне Telegram показывать отдельный экран, а для локальной разработки использовать только явный dev-режим;
- dev-режим запрещён в production;
- не логировать токен бота и полный `initData`.

### Проверка

- валидный вход из Telegram успешен;
- изменённая строка `initData` получает 401;
- просроченная строка получает 401;
- прямой браузерный запрос не создаёт пользователя;
- production build не содержит токен бота.

## Этап 3. Семья, участники и приглашения

Статус: реализован 1 октября 2026. Локально пройдены 24 автотеста и браузерный сценарий с двумя профилями. Инструкция проверки: `docs/FAMILY_CHECK.md`; подготовка первого развёртывания: `docs/FIRST_RELEASE.md`. Развёртывание и проверка двумя реальными Telegram-аккаунтами ожидают доступа к VPS и настройки бота.

### Задача

Реализовать создание одной семьи на пользователя и вступление по ссылке.

### Требования

- экран первого входа без семьи;
- создание семьи делает пользователя владельцем;
- один пользователь не может вступить во вторую семью;
- владелец создаёт и отзывает приглашения;
- приглашение открывает бота/Mini App с параметром токена;
- токен проверяется сервером;
- владелец может удалить участника;
- только владелец может изменить название и часовой пояс семьи через настройки и `PATCH /api/family`;
- часовой пояс по умолчанию `Europe/Moscow`, начало недели — понедельник;
- обычный участник не может управлять приглашениями и составом;
- сервер не доверяет `family_id`, присланному клиентом.

### Проверка

- два тестовых Telegram-пользователя вступают в одну семью;
- повторное вступление не создаёт дубликат;
- вступление во вторую семью отклоняется;
- отозванная и истёкшая ссылки не работают;
- участник не получает данные другой семьи;
- владелец меняет название и часовой пояс, обычный участник получает отказ;
- настройки сохраняются после перезапуска.

## Этап 6. Дела: базовая модель и экран «Сегодня»

### Задача

Реализовать персональные списки дел, права доступа, AI-разбор, выполнение и дневную просрочку.

### Требования

- у каждого зарегистрированного участника отдельный список;
- свой список открывается по умолчанию;
- можно перейти в список другого зарегистрированного участника семьи;
- гостевые профили вишлистов не являются владельцами списков дел;
- владелец полностью управляет делами собственного списка;
- другой участник может только просматривать список и добавлять новое дело;
- после сохранения автор не может редактировать, переносить, выполнять или удалять чужое дело;
- хранить `owner_user_id` и `created_by_user_id`, но не показывать их как поля формы;
- кнопка добавления доступна на главном экране и внутри списка;
- с главного экрана можно выбрать владельца, по умолчанию текущего пользователя;
- внутри списка владелец определяется контекстом;
- добавить endpoint предварительного AI-разбора текста;
- AI выделяет название, описание, дату и необязательное время;
- результат AI показывается для ручного исправления до сохранения;
- при ошибке AI доступно ручное заполнение;
- дело на точную дату;
- просмотр выбранной даты;
- переключение даты стрелками, жестом и календарём;
- complete/reopen;
- выполненные по умолчанию скрыты;
- фильтр «Невыполненные / Все»;
- сортировка активных дел по времени по возрастанию;
- дела без времени ниже дел со временем;
- выполненные в режиме «Все» ниже активных;
- компактная карточка и отдельные детали с полным описанием, автором и датой создания;
- выполненные дела сохраняются в истории по фактической дате выполнения в часовом поясе семьи;
- автоматическая видимость невыполненных прошлых дел сегодня;
- хранить первоначальную дату для истории и актуальный плановый срок для расчёта просрочки;
- ручной перенос снимает просрочку от старого срока; новая просрочка возникает только после окончания нового срока;
- вчерашние выделять красным, более старые — бордовым;
- цвет не должен быть единственным признаком просрочки: добавить текст/иконку.

### Проверка

- просрочка правильно определяется на границе суток часового пояса семьи;
- завершённое просроченное дело исчезает из активных и показывается в истории на дате выполнения;
- ручной перенос на завтра снимает прежнюю просрочку;
- reopen возвращает правильное состояние;
- нельзя добавить дело пользователю из другой семьи;
- автор не может изменить созданное им чужое дело;
- владелец списка может изменить и выполнить добавленное ему дело;
- при недоступности AI дело создаётся вручную.

## Этап 7. Дела: неделя и месяц

### Задача

Добавить дела без точного дня и календарные представления.

### Требования

- типы периода `date`, `week`, `month`;
- дело недели/месяца может не иметь точного дня;
- неделя: режимы «По дням» и «Без даты»;
- месяц: календарная сетка в режиме «По дням» и отдельный режим «Без даты»;
- при добавлении AI определяет конкретный день либо оставляет дело без даты в текущем периоде;
- в собственном списке доступен drag-and-drop между днями;
- доступная альтернатива «Перенести» через форму/меню;
- перенос и редактирование в чужом списке запрещены;
- единый фильтр статуса;
- недельные дела без даты переносятся в следующую неделю с исходным периодом и признаком просрочки;
- месячные дела без даты переносятся в следующий месяц с исходным периодом и признаком просрочки;
- один прошлый период выделяется красным, два и более — бордовым;
- просрочка дополнительно объясняется текстом, а не только цветом;
- неделя начинается в понедельник, границы периодов рассчитываются в часовом поясе семьи;
- ручной перенос на другую неделю или месяц устанавливает новый срок без прежней просрочки;
- выполненные дела без даты показываются в истории по фактической дате выполнения.

### Проверка

- перенос между днями сохраняется после перезагрузки;
- дело без дня не исчезает из недельного/месячного представления;
- просроченные дела без даты видны в текущем периоде и сохраняют исходный период;
- переходы между месяцами не создают неверные даты;
- ручной перенос недельного или месячного дела снимает прежнюю просрочку;
- история выполненных дел без даты использует дату выполнения.

## Этап 8. Вишлисты

### Задача

Реализовать профили вишлистов для участников семьи и людей без Telegram.

### Требования

- таблица и API профилей вишлистов;
- любой авторизованный участник семьи вручную создаёт профиль для любого человека: себя, участника семьи, ребёнка, друга или родственника;
- профиль хранит имя, необязательную подпись или аватар и не требует привязки к `user_id`;
- человеку из профиля не нужны аккаунт или авторизация; создание профиля не даёт доступ к семье;
- при вступлении в семью профиль вишлиста автоматически не создаётся;
- список профилей и переход в каждый вишлист;
- все участники семьи могут создать, изменить и удалить пункт;
- все участники могут отметить пункт исполненным или вернуть в активное состояние;
- поля: название, URL, заметка, цена;
- URL валидируется;
- исполненные пункты зачёркнуты;
- профиль можно переименовать или удалить только его создателю либо владельцу семьи;
- удаление любого профиля каскадно удаляет его пункты только после подтверждения;
- сервер всегда проверяет принадлежность профиля и пункта текущей семье.

### Проверка

- участник создаёт гостевой профиль без Telegram-аккаунта;
- другой участник семьи добавляет и редактирует пункты этого вишлиста;
- посторонний участник не может переименовать или удалить гостевой профиль;
- владелец семьи может удалить гостевой профиль;
- профиль для зарегистрированного участника создаётся вручную и подчиняется общим правам удаления;
- вступление в семью не создаёт и не связывает профили автоматически;
- данные разных семей изолированы.

## Этап 9. Telegram-уведомления

### Задача

Добавить ежедневную сводку в 09:00 по часовому поясу семьи и немедленное уведомление о новом чужом деле.

### Требования

- серверный планировщик;
- часовой пояс семьи;
- сводка ежедневно в 09:00 по часовому поясу семьи;
- личные невыполненные дела получателя на сегодня, включая автоматически перенесённые, в утреннем сообщении;
- немедленное уведомление, если другой участник добавил дело в список пользователя;
- в уведомлении указать автора, название, дату и время;
- ошибка уведомления не откатывает создание дела;
- кнопка открытия Mini App;
- `notification_deliveries` для идемпотентности;
- повторный запуск процесса не дублирует сообщение;
- ошибки Telegram API логируются без секретов и не останавливают рассылку другим пользователям;
- предусмотреть выключение рассылки переменной окружения для разработки.

### Проверка

- тестовый запуск отправляет ожидаемую сводку в 09:00 по часовому поясу семьи;
- второй запуск того же периода не отправляет дубль;
- сообщение содержит только данные семьи получателя;
- добавление дела другому пользователю создаёт одно немедленное уведомление;
- ошибка одного chat ID не ломает остальные отправки.

Безопасно обновлять существующий VPS в указанных выше точках развёртывания. После этапа 10 выполнить итоговую приёмку MVP.

### Порядок

1. Создать резервную копию текущих данных и `.env`.
2. Получить изменения из Git.
3. Проверить production-переменные окружения.
4. Собрать новый image.
5. Выполнить миграции отдельной командой.
6. Запустить контейнер.
7. Проверить health endpoint и логи.
8. Выполнить smoke test внутри Telegram двумя пользователями.
9. Проверить Caddy и HTTPS.
10. Начиная с релиза этапа 9 проверить пробное уведомление.

### Команды

Точные команды Codex должен адаптировать к фактическим scripts репозитория после этапа 0. Нельзя придумывать имена npm-скриптов или миграционных команд до аудита.

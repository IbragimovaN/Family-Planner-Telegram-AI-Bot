# Текущее состояние Family Planner

Дата аудита: 30 сентября 2026. Этап 0 из `doc/CODEX_PLAN.md`.
Проверен локальный репозиторий; состояние VPS не проверялось. Поведение приложения не изменялось. Значения секретов и содержимое пользовательских задач не читались и не включены в отчёт.

## Основной результат

Это работающий прототип общего списка задач с React, Express, SQLite и AI-разбором. Предположение этапов 0–1 о JSON-хранилище устарело: приложение уже использует `better-sqlite3`. Следующий этап должен мигрировать существующую SQLite-схему, а не заменять JSON.

Telegram-авторизации, семей, разграничения доступа, календарных периодов, покупок, вишлистов и уведомлений пока нет. Текущий интерфейс доступен в обычном браузере. Это разрыв между прототипом и целевой спецификацией; в рамках аудита он только зафиксирован. Реализация следующих этапов не начата.

## Структура и запуск

| Файл | Фактическая ответственность |
| --- | --- |
| `src/main.tsx` | React root и StrictMode |
| `src/App.tsx` | Один экран, загрузка списка, ручное создание, выполнение, фильтр, AI-форма |
| `src/api/tasksApi.ts` | Fetch-запросы к относительным `/api` URL |
| `src/types/task.ts` | Клиентский тип задачи |
| `src/App.css`, `src/index.css` | Адаптивные стили, системная светлая/тёмная тема |
| `server/src/index.ts` | Express, пять API-маршрутов, SQL-запросы, раздача SPA |
| `server/src/database.ts` | Открытие SQLite, WAL, создание таблицы |
| `server/src/ai.ts` | OpenAI-клиент, структурированный разбор текста через Zod |
| `vite.config.ts` | React plugin и dev-прокси `/api` на `localhost:3000` |

Frontend: React 19, TypeScript 6, Vite 8 согласно manifest. Backend: Express 5, `better-sqlite3` 13, OpenAI SDK 7, Zod 4. У корня и `server` отдельные package.json и lock-файлы. Корневые devDependencies предоставляют TypeScript и tsx также для backend; установки только пакетов `server` недостаточно для воспроизводимой разработки и сборки сервера.

Локальное окружение аудита: Node v24.8.0, npm 11.6.0, Windows PowerShell. README требует Node 22.12+, Docker использует Node 24.

Разработка: `npm run server-dev` из `server` и `npm run dev` из корня. Production: `npm run build`, `npm run build --prefix server`, затем `npm start --prefix server`.

Express слушает `0.0.0.0`, порт берётся из `PORT` либо равен 3000. Путь frontend вычисляется от файла backend как `../../dist`: и для `server/src`, и для `server/dist` он ведёт в корневой `dist`. После API подключён `express.static`; остальные пути, не начинающиеся с `/api`, получают `index.html`. Неизвестный API не получает SPA, но отдельного JSON-обработчика 404 нет. CORS разрешает origin `http://localhost:5173`; это не механизм авторизации.

## Фактические API

Все маршруты подтверждены по `server/src/index.ts`. Авторизации и проверки семьи нет ни на одном из них.

| Метод и путь | Вход | Ответ и поведение |
| --- | --- | --- |
| `GET /api/health` | — | 200, `{status: "ok"}`; запрос к БД не выполняется |
| `GET /api/tasks` | — | 200, массив `{id, title, completed}`, сортировка `created_at ASC`; фильтров и пагинации нет |
| `POST /api/tasks` | `{title: string}` | Непустая строка после trim; 201 с новой задачей, UUID, `completed=false`; 400 при неверном названии |
| `PATCH /api/tasks/:id/toggle` | ID | Инвертирует состояние, 200 с задачей; 404 для отсутствующего ID |
| `POST /api/ai/tasks` | `{text: string}` | 200, `{tasks: string[]}`; 400 для пустого/нестрокового текста, 500 при ошибке AI; сам задачи не сохраняет |

Проверка полей ручная, а не общая schema validation тела запроса. Нет редактирования, удаления, complete/reopen с явным целевым состоянием, дат, владельцев, авторов и описаний. Общий обработчик ошибок с единым JSON-контрактом отсутствует.

## Хранилище и модель

`server/src/database.ts` создаёт каталог `server/data`, открывает `family-planner.db`, включает `journal_mode=WAL` и выполняет `CREATE TABLE IF NOT EXISTS tasks`. Это происходит при импорте модуля.

| Поле таблицы `tasks` | Тип и ограничение |
| --- | --- |
| `id` | TEXT PRIMARY KEY |
| `title` | TEXT NOT NULL |
| `completed` | INTEGER NOT NULL DEFAULT 0 |
| `created_at` | TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP |

API преобразует числовое `completed` в boolean и не возвращает `created_at`. Отдельного индекса сортировки, таблицы версий миграций, миграционных команд и настройки foreign keys в исходниках нет. `DATABASE_PATH` не поддерживается; путь фиксирован относительно модуля. Схема описана по исходникам, содержимое локальной базы не исследовалось.

Локально присутствуют файлы `family-planner.db`, `family-planner.db-wal`, `family-planner.db-shm`. Приложение в ходе аудита не запускалось, данные не изменялись.

### Все места работы с JSON

Файлового JSON-хранилища, чтения/записи JSON-файлов, localStorage или sessionStorage в `src` и `server/src` не найдено. `node:fs` используется только для `mkdirSync` в модуле БД.

- `src/api/tasksApi.ts`: `JSON.stringify` формирует тела создания и AI-разбора; `response.json()` читает ответы всех четырёх клиентских операций.
- `server/src/index.ts`: `express.json()` разбирает вход; `response.json()` возвращает API-ответы и ошибки.
- `server/src/ai.ts`: Zod описывает структурированный ответ внешнего AI; он не является хранилищем.
- package.json, lock-файлы и tsconfig — конфигурационные JSON, а не пользовательские данные.

## AI и интерфейс

`server/src/ai.ts` создаёт OpenAI-клиент при импорте. Модель задана строкой `gpt-5.6-luna`; переменной выбора модели нет. Используется `responses.parse` с Zod-схемой массива объектов `{title}`. Доступность модели и внешнего API аудитом не проверялась; платные запросы не выполнялись.

После разбора frontend немедленно создаёт все задачи через `Promise.all`, без предварительного просмотра и подтверждения. При частичном сбое часть задач может уже сохраниться, но не отобразиться до обновления страницы. Нет разбора дат, времени, описания и контекста часового пояса. Ручная форма существует отдельно; автоматического переключения AI-формы на ручное заполнение нет. Инициализация клиента зависит от ключа даже для запуска не-AI функций.

Интерфейс уже содержит загрузку, текст ошибки, пустое состояние, скрытие выполненных, зачёркивание, адаптивные формы и focus-стили. Кнопки и текстовые поля имеют min-height 44px. Темы следуют `prefers-color-scheme`, а не Telegram. Нет маршрутизации, Telegram SDK, BackButton, safe area, сессий, календаря и семейного контекста. Обычная отправка и toggle не блокируются на время запроса; повторные клики могут создавать дубли или переключать состояние повторно.

## Переменные окружения и секреты

| Переменная | Использование |
| --- | --- |
| `OPENAI_API_KEY` | Читается OpenAI SDK при `new OpenAI()`; документирована в README, нужна для запуска текущего backend |

`dotenv/config` импортируется AI-модулем, `dotenv.config()` также вызывается в index.ts. По умолчанию .env ищется относительно рабочего каталога процесса; документированный запуск из `server` важен. Compose передаёт `server/.env` как окружение контейнера. Файл .env не читался, его значения и полнота не проверялись. Имена выше подтверждены кодом и документацией, а не содержимым секретного файла.

Frontend не обращается к переменным окружения. Telegram bot token, настройки сессий, расписания и DATABASE_PATH пока не реализованы. .gitignore исключает .env и три файла SQLite по маскам; .dockerignore также исключает `.env.*` и весь `server/data`. В текущем списке отслеживаемых Git файлов .env и БД отсутствуют; история Git на секреты не проверялась. Ошибки AI логируются целым объектом: для MVP нужна проверка и фильтрация чувствительных данных в логах.

## Docker и эксплуатация

Dockerfile многостадийный: Node 24 bookworm-slim, установка python3/make/g++ для native-модуля SQLite, `npm ci` для обоих пакетов, обе сборки, отдельная установка production-зависимостей backend. Финальный образ содержит `/app/dist`, `/app/server/dist` и backend dependencies. Рабочая директория `/app/server`, запуск от пользователя `node`, порт 3000.

Compose описывает один сервис `app`, restart `unless-stopped`, `init: true`, env_file, фиксированные NODE_ENV и PORT. Именованный volume `server-data` подключён к `/app/server/data`. Он сохраняется при обычном `docker compose down`; локальная база автоматически в него не импортируется. Смена имени Compose-проекта может подключить другой том и выглядеть как потеря данных.

Healthcheck проверяет лишь успешный HTTP-ответ `/api/health`; работоспособность запросов к БД не подтверждает. Backup, ротации и восстановления в репозитории нет.

**Прямое расхождение со спецификацией:** Compose публикует `3000:3000`, тогда как SPEC требует внешние 80/443 через Caddy и SSH. Caddy, доменная конфигурация и HTTPS в репозитории отсутствуют; нельзя заключить, что их нет отдельно на VPS. До первого релиза нужно проверить фактический reverse proxy и схему сети.

## Риски миграции и решения перед этапом 1

1. **Существующая SQLite вместо JSON.** Нужны версионированные миграции и проверка на существующей таблице `tasks`; `CREATE TABLE IF NOT EXISTS` не обновит её структуру. Уже выбранную better-sqlite3 следует оценить с учётом целевого Node и native-сборки.
2. **Нет принадлежности старых задач.** В данных нет family_id, owner_user_id и created_by_user_id. Перед миграцией пользователь должен выбрать: сохранить задачи с явным назначением семье/участнику или начать с пустой БД после резервного копирования. Нельзя самостоятельно назначать владельца или удалять данные.
3. **Нет даты выполнения и планового срока.** Достоверно восстановить историю выполнения из completed и created_at нельзя. Эти поля нельзя выдавать за фактическую дату завершения. Нужна политика для старых задач.
4. **WAL и резервные копии.** Копирование одного активного .db может пропустить изменения из WAL. Нужен согласованный SQLite backup либо корректно остановленная и сохранённая база с учётом WAL; восстановление проверить отдельно.
5. **Открытые старые API.** При добавлении авторизации нужно закрыть и существующие endpoints, включая AI. До первого релиза этапов 1–3 проверить отсутствие обхода через прежние маршруты, изоляцию семей и cookies за reverse proxy.
6. **Изменение контракта задач.** Toggle заменить целевыми complete/reopen и согласовать frontend/backend. Для переноса различать первоначальный и актуальный плановый срок; историю строить по фактическому выполнению. Старые boolean-данные этого не обеспечивают.
7. **AI создаёт задачи без подтверждения.** Текущую схему parse + автоматические POST потребуется заменить предварительным разбором и ручной проверкой. Исключить частичные массовые сохранения и обеспечить ручное создание при недоступности AI.
8. **Инфраструктура расходится с SPEC.** Проверить VPS/Caddy, закрыть прямую публикацию 3000 согласно фактической сети, сохранить существующий volume и права пользователя node. Не считать локальный Compose описанием всей инфраструктуры VPS.
9. **Защита и наблюдаемость.** Нет сессий, rate limit, единых схем валидации, application security headers, проверки БД в health и автоматических backup. Критические меры нужны к первому релизу, остальные — по плану.
10. **Проверки пока без тестов.** Перед изменением данных и прав добавить содержательные интеграционные тесты. Docker/native SQLite и восстановление проверить в среде с работающим Engine.

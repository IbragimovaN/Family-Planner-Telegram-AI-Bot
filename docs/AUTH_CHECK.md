# Проверка Telegram-авторизации — этап 2

На этом этапе работают вход, сессия, выход и временный список задач прототипа. Создание семьи и приглашения появятся на этапе 3. Выход кнопкой «Выйти» завершает только сессию приложения — это не выход из семьи.

## 1. Быстрая проверка на компьютере без Telegram

Все команды выполняются в терминале из папки `family-planner-bot`.

Подготовка после получения изменений:

```powershell
npm run build --prefix server
npm run db:migrate --prefix server
```

Если база ещё не создавалась, вместо `db:migrate` первый раз выполните `npm run db:init --prefix server`. У вас база уже создана на этапе 1. Повторно очищать её не нужно.

Откройте **два терминала**. В первом:

```powershell
npm run server-dev:auth --prefix server
```

Во втором:

```powershell
npm run dev
```

Откройте **http://localhost:5173**. Используйте именно этот адрес, не `127.0.0.1` и не порт 3000: проверка источника запросов ожидает `localhost:5173`. Если порт занят, остановите ранее запущенную копию приложения; Vite намеренно не выбирает другой порт.

Если порт 3000 занят другой копией или Docker и вы не хотите её останавливать, используйте порт 3001. В первом терминале перед запуском сервера выполните `$env:PORT="3001"`, во втором перед запуском Vite — `$env:DEV_API_PORT="3001"`. Адрес страницы остаётся http://localhost:5173. Эти переменные действуют только в соответствующих терминалах.

Что проверить:

1. Видна кнопка «Войти как тестовый пользователь». Нажмите её.
2. Вверху появится «Вы вошли как Тестовый пользователь · Тестовый вход», ниже — список задач.
3. Добавьте задачу вручную, отметьте выполненной, включите «Показать все».
4. Обновите страницу: вход и задача сохранятся.
5. Нажмите «Выйти»: список исчезнет, появится экран выхода.
6. Откройте http://localhost:5173/api/me после выхода: ответ 401 с сообщением о завершённой сессии.
7. Войдите снова: сохранённая задача останется у тестового пользователя.

Этот режим не проверяет настоящую подпись Telegram. Он специально создаёт локальный тестовый профиль `dev:local`, а не подменяет реальный Telegram-аккаунт. Команда включает режим только в запущенном процессе и не меняет `.env`. Сервер слушает только `127.0.0.1`; не публикуйте его через туннель в этом режиме.

Для остановки нажмите Ctrl+C в обоих терминалах. Тестовые задачи сохраняются в вашей локальной БД. Проверки автоматических тестов, в отличие от ручного добавления, используют временные базы.

## 2. Проверка запрета входа из обычного браузера

Остановите сервер из пункта 1. Запустите обычный режим:

```powershell
npm run server-dev --prefix server
```

В `.env` и окружении не должно быть `DEV_AUTH_ENABLED=true`. Vite во втором терминале можно оставить включённым.

Обновите http://localhost:5173: должен появиться экран «Откройте приложение через бота», без кнопки тестового входа и списка задач. Даже ранее выданная dev-сессия перестаёт работать после отключения dev-режима. Запрос к `/api/me` или `/api/tasks` без действительной сессии вернёт 401. Само открытие сайта не создаёт пользователя.

В DevTools → Application → Cookies локальная cookie `family_session` должна иметь HttpOnly, SameSite=Lax и Path=/. В HTTPS-режиме используется `__Host-family_session` с Secure, HttpOnly, SameSite=None и без Domain. JavaScript приложения не читает cookie.

## 3. Что понадобится для настоящего входа через Telegram

- Токен именно того бота, из которого открывается приложение. Добавьте его только в `server/.env` как `TELEGRAM_BOT_TOKEN=...`; не отправляйте в чат и не используйте префикс `VITE_`.
- HTTPS-адрес, на котором доступна **эта версия** frontend и backend с одним origin.
- Настроенная кнопка Mini App у бота. В [BotFather](https://t.me/BotFather) команда `/setmenubutton` позволяет выбрать бота, указать HTTPS URL приложения и подпись кнопки. Обычная ссылка в чате, открывающая браузер, не заменяет кнопку Mini App.

Настройки сервера для будущего релиза:

```dotenv
NODE_ENV=production
APP_ORIGIN=https://planner-bot.ibragimova-apps.ru
TELEGRAM_BOT_TOKEN=значение_из_BotFather
DEV_AUTH_ENABLED=false
```

`APP_ORIGIN` — только схема и домен, без пути. Для отдельного тестового HTTPS-адреса укажите его вместо production-домена и настройте URL тестового бота на него. Сервер откажется запускаться с `DEV_AUTH_ENABLED=true` в production. OpenAI-ключ для проверки входа не нужен; он используется только при нажатии AI-кнопки.

По согласованному плану VPS обновляется после этапов 1–3, поэтому открытие нынешнего сайта на VPS пока не проверяет этот код. Сейчас доступна локальная проверка выше; реальную проверку Telegram можно выполнить после совместного релиза или на отдельно подготовленном HTTPS-стенде с тестовым ботом.

После размещения этой версии:

1. Откройте чат с нужным ботом и Mini App через его кнопку. Вход происходит автоматически, вверху отображается ваше имя.
2. Добавьте задачу, закройте Mini App и откройте снова: сессия и данные сохраняются.
3. Нажмите «Выйти»: API больше не принимает прежнюю сессию. Повторный вход возможен через кнопку; если данные запуска старше 5 минут, закройте Mini App полностью и откройте снова.
4. Второй Telegram-аккаунт получает отдельный профиль и не видит ваши временные задачи.
5. Открытие того же HTTPS URL вне Telegram показывает экран перехода к боту.

Сессия действует 7 дней. После её истечения нужно снова открыть Mini App. Некорректная подпись, старые данные и неизвестный пользователь без корректного `initData` не создают аккаунт. Cookie SameSite=None нужна для HTTPS WebView/встраивания; если браузер полностью блокирует сторонние cookies, используйте мобильный клиент Telegram для проверки.

## 4. Автоматические проверки

Из корня проекта:

```powershell
npm run lint
npm run build
npm run build --prefix server
npm run typecheck --prefix server
npm test --prefix server
```

Тесты используют вымышленные Telegram ID и тестовый ключ, не обращаются к Telegram или OpenAI и не меняют вашу БД. Они проверяют подпись и срок `initData`, отсутствие анонимного доступа, cookie и хеш сессии, logout, срок сессии, CSRF-защиту, rate limit, запрет dev-входа в production, разделение задач и сохранение сессии после перезапуска.

## Технические решения

- Проверяется исходная строка `Telegram.WebApp.initData`, HMAC-SHA256 и `auth_date` (до 5 минут, допустимое опережение часов — 30 секунд). `initDataUnsafe` не используется.
- Сессия — случайный 256-битный токен в HttpOnly cookie. В SQLite только SHA-256 токена; повторный вход обновляет профиль и заменяет текущую сессию.
- Все `/api` после health и маршрутов авторизации закрыты общим middleware. Logout требует сессию. Все изменяющие запросы требуют точный Origin, JSON и заголовок `X-Family-Planner: 1`. CORS для сторонних источников не включён.
- Вход ограничен 20 попытками в минуту на IP процесса. Forwarded-заголовки не используются для доверенного определения IP. За reverse proxy лимит может быть общим для посетителей; схему доверия к proxy нужно уточнить перед первым релизом.
- Миграция 2 добавляет вид сессии и владельца временных задач. Прежние задачи без владельца сохраняются в БД, но не выдаются ни одному пользователю и не присваиваются первому вошедшему.
- Новые файлы: `server/src/auth/*`, `server/src/app.ts`, `src/AuthGate.tsx`, `src/api/http.ts`, тесты авторизации. Миграция 1 не изменена.

Основание для проверки подписи и подключения SDK: [официальная документация Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app); [настройка кнопки меню](https://core.telegram.org/bots/webapps#launching-mini-apps-from-the-menu-button).

## Результаты проверки реализации

30 сентября 2026: lint, frontend build/typecheck, backend build/typecheck и 18 автотестов прошли. В Chromium с мобильной шириной проверены тестовый вход, создание задачи, HttpOnly-cookie, обновление страницы, выход, повторный вход и запрет dev-сессии после выключения режима. Для браузерной проверки использована временная база; настоящий Telegram SDK заменён пустым объектом запуска, поэтому эта проверка не является входом из Telegram.

Миграция 2 применена к локальной базе после автоматического backup. Проверено, что существующие серверные секреты отсутствуют в frontend-сборке. На момент проверки в `server/.env` нет `TELEGRAM_BOT_TOKEN`; настоящий вход из Telegram ещё не проверялся. VPS не обновлялся.

Production Docker-образ успешно собран. В одноразовом контейнере проверены запуск без OpenAI-ключа, отказ анонимному запросу, вход по тестовой HMAC-подписи, Secure/HttpOnly-cookie и отказ запуска с dev-режимом. Использован вымышленный токен, обращений к Telegram не было.

# Этапы 6–7: персональные дела

## Аудит перед реализацией

Ветка `step67`, 10 октября 2026. До изменений раздел дел использовал `prototype_tasks`: личные названия и чекбокс без дат, описаний и семейного доступа. AI возвращал несколько названий, которые сохранялись сразу. Таблица `tasks` уже была создана миграцией 1, но не использовалась приложением.

Существующие авторизация, семьи, приглашения, продукты с AI-сортировкой, история закрытых списков и отдельные покупки переиспользованы без изменения контрактов. Согласованная светлая тема сохранена. Docker и конфигурация продакшена не изменены.

## Реализация

- `server/src/tasks.ts`: семейные списки, проверка владельца на каждой мутации, создание до 20 дел одной транзакцией, предварительный AI-разбор без сохранения.
- `server/src/task-dates.ts`: гражданские даты в часовом поясе семьи; понедельник как начало недели; вычисляемая просрочка без фонового переноса записей.
- `server/src/task-input.ts`, `tasks-ai.ts`: валидация реальных дат, времени, начала периода; ограниченный по времени AI-запрос; ручной fallback и ограничение частоты.
- `src/Tasks.tsx`, `task-calendar.ts`: сегодня/выбранный день, неделя, месяц, режимы «По дням»/«Без даты», выбор участника, предпросмотр нескольких задач, детали, подтверждение удаления, перенос формой и drag-and-drop.
- Кнопка «Добавить дело» на главной открывает форму с выбором участника. Внутри списка владелец задан контекстом.
- Завершение идемпотентно: повторный запрос не меняет дату выполнения. История использует дату фактического выполнения в часовом поясе семьи. Ручное изменение срока сохраняет первоначальный срок и снимает прежнюю просрочку.
- Уведомления и повторяющиеся дела не добавлены: уведомления относятся к этапу 9.

## Сохранность прежних задач

Миграция **5** добавляет только `task_legacy_imports`. При первом чтении списка сервер в транзакции переносит принадлежащие этому пользователю старые задачи в `tasks`. Таблица соответствия предотвращает повторный импорт, в том числе после удаления нового дела. Исходные строки `prototype_tasks` остаются нетронутыми. Записи без владельца не присваиваются произвольному пользователю.

У старых задач не было плановой даты: при импорте используется дата создания в часовом поясе семьи, что поясняется в описании. У выполненных задач также не было даты выполнения: они появляются в истории в день импорта с явной поясняющей заметкой. Это не восстановленная историческая дата.

Старый API прототипа сохранён отдельно по `/api/prototype-tasks` и `/api/prototype-tasks/:id/toggle`, с прежней пользовательской изоляцией. Новый экран его не использует. `/api/ai/tasks` сохранён для совместимости; новый предпросмотр использует `/api/tasks/parse`.

## Новый API

- `GET /api/tasks?owner=<userId>&period=date|week|month&date=YYYY-MM-DD&mode=days|undated&status=active|all`.
  По умолчанию свой список на сегодня. Ответ: `tasks`, `today`, `timezone`, `ownerUserId`, `canEdit`.
- `POST /api/tasks`: `{ ownerUserId, tasks: [{ title, description, periodType, plannedDate, plannedTime }] }`.
- `POST /api/tasks/parse`: `{ text, periodType, date }`; возвращает `{ tasks }`, ничего не сохраняет.
- `PATCH /api/tasks/:id`: полная редактируемая форма `{ title, description, periodType, plannedDate, plannedTime }`.
- `POST /api/tasks/:id/complete`, `POST /api/tasks/:id/reopen`, `DELETE /api/tasks/:id`: тело `{}`.

Для недели `plannedDate` — понедельник, для месяца — первое число; время допускается только у точной даты. Для просмотра чужого списка и создания дела нужен действующий участник той же семьи. Редактировать/выполнять/удалять может только владелец списка, а не автор или владелец семьи.

AI использует `OPENAI_API_KEY` и необязательный `TASKS_AI_MODEL` (по умолчанию существующая в проекте модель `gpt-5.6-luna`). Клиент создаётся только при разборе; отсутствие ключа не препятствует запуску приложения или ручному вводу. Реальный AI-запрос в автоматических проверках не выполняется.

## Локальные проверки

```sh
npm run build --prefix server
npm test --prefix server
npm run typecheck --prefix server
npm run lint
npm run build
```

`server/test/tasks.test.mjs` проверяет семейную изоляцию и права автора/владельца, реальные даты и границы часовых поясов, сортировку, дневную/недельную/месячную просрочку, перенос и исходный срок, идемпотентное выполнение, reopen, AI-предпросмотр и неверный результат AI, удаление участника во время AI-запроса, однократный импорт старых данных. Тесты используют базы в памяти и искусственные часы.

Браузерная проверка через существующий CDP-скрипт не стартует в текущей среде: Chrome и Edge возвращают тайм-аут `Page.enable`. Проверка на реальном Telegram остаётся обязательной; её прохождение не заявляется.

## Ручная приёмка

1. Открыть «Список дел»: свой список, текущая дата семьи, невыполненные по умолчанию. Проверить стрелки, выбор даты и горизонтальный свайп по строке даты.
2. Добавить дело вручную и через AI; до «Сохранить» данные не должны появляться в списке. Вручную изменить результат AI. При недоступном AI заполнить форму.
3. Проверить несколько дел из одной фразы, удалить лишний результат перед сохранением.
4. С главной добавить дело другому участнику. В его списке просмотреть детали; выполнение, редактирование и удаление недоступны. Войти этим участником и выполнить дело.
5. Создать дело на вчера/позавчера: проверить красную/бордовую границу и текст просрочки сегодня. Выполнить; проверить «Все» на фактической дате выполнения. Вернуть в активные и перенести на завтра.
6. «Неделя → Без даты»: добавить дело без дня; «По дням»: перетащить дневное дело на другую секцию. На сенсорном устройстве проверить перенос через детали как доступную альтернативу.
7. «Месяц → По дням»: проверить календарь, индикаторы, выбор дня, февраль/високосный год и переход декабрь→январь. «Без даты»: добавить месячное дело.
8. Проверить формы на ширинах 320/375/430 px, клавиатуру, Escape/Telegram BackButton, отмену, ошибки, отсутствие повторного сохранения.
9. Повторно проверить продукты (добавление, AI, закрытие, история), обычные покупки, настройки семьи и приглашения.

## Подготовка обновления VPS (не выполнялась)

После согласования и публикации ветки необходима миграция **5** до запуска нового сервера. Не использовать `db:init`, не удалять volumes.

В `/opt/family-planner`, после получения согласованного коммита:

```sh
docker compose build app
docker compose stop app
docker compose run --rm --no-deps app npm run db:backup
docker compose run --rm --no-deps app npm run db:migrate
docker compose up -d app
docker compose logs --tail=50 --no-color app
curl -i http://localhost:3000/api/health
```

Выполнять по очереди, останавливаясь при ошибках. Мигратор дополнительно создаёт backup перед применением миграции. Сервер проверяет схему при запуске и не выполняет автоматическую миграцию.

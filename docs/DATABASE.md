# SQLite: этап 1

Дополнение этапа 2: появилась миграция авторизации и владельцев временных задач. Актуальный вход и проверка API описаны в [AUTH_CHECK.md](AUTH_CHECK.md); описание открытого прототипа ниже относится к состоянию на конец этапа 1.

Используется уже установленная `better-sqlite3`, без новой ORM. Проверена загрузка native-модуля на локальном Node 24.8.0 и в собранном Linux-образе Docker на Node 24.

## Пустая база вместо импорта

Решение пользователя: не переносить старые задачи. Старый файл `server/data/family-planner.db` остаётся на месте. Новая база по умолчанию — `server/data/family-planner-v2.db`. Не удаляйте старый файл или WAL до проверки резервной копии.

Остановите старый сервер, затем из корня проекта выполните:

```sh
npm run build --prefix server
npm run db:init --prefix server
```

Команда делает SQLite backup старой базы с учётом WAL, проверяет `integrity_check`, затем эксклюзивно создаёт новый файл и применяет миграции. Если резервное копирование не удалось, новая база не создаётся. Существующий целевой файл никогда не перезаписывается. При ошибке первой миграции созданный файл может остаться пустым: исправьте причину и выполните `db:migrate`, повторный `db:init` не нужен.

Для старой базы в другом месте передайте её путь явно:

```sh
npm run db:init --prefix server -- /absolute/path/to/old.db
```

Явный путь должен существовать. Без аргумента отсутствие стандартного старого файла допустимо для новой установки. Новая БД не содержит пользователей, семей или задач; исходные записи не импортируются.

## Настройки и команды

`server/.env` загружается по абсолютному пути к каталогу сервера; заданные переменные процесса имеют приоритет. Относительные значения `DATABASE_PATH` и `DATABASE_BACKUP_DIR` считаются от `server/`. По умолчанию это `data/family-planner-v2.db` и `data/backups`. Compose задаёт абсолютные пути в существующем томе `server-data`.

| Команда из корня | Назначение |
| --- | --- |
| `npm run db:init --prefix server` | Однократная подготовка нового файла и backup прежней базы |
| `npm run db:migrate --prefix server` | Backup перед ожидающими миграциями, затем транзакционное обновление |
| `npm run db:backup --prefix server` | Согласованная копия текущей базы с проверкой целостности |

Команды запускают скомпилированный код: сначала выполните `npm run build --prefix server`. Для новых изменений схемы остановите сервер до backup/миграции. При повторной миграции применяется 0 версий, данные сохраняются. Сервер сам схему не создаёт и не обновляет: без подготовленной БД или при ожидающих миграциях запуск прекращается.

Миграции находятся в `server/src/db/schema.ts`; журнал `schema_migrations` хранит номер, название, SHA-256 SQL и время применения. Вся группа ожидающих миграций выполняется в `BEGIN IMMEDIATE`: ошибка откатывает и DDL, и журнал. Изменённая, неизвестная или пропущенная история версий отклоняется. Уже применённый SQL нельзя редактировать — добавляйте следующую версию. База старого прототипа без журнала миграций отклоняется, а не преобразуется автоматически.

## Схема и границы ответственности

Созданы все 11 таблиц SPEC: `users`, `families`, `family_members`, `invitations`, `sessions`, `shopping_lists`, `shopping_items`, `tasks`, `wishlist_profiles`, `wishlist_items`, `notification_deliveries`.

- На каждом соединении включены foreign keys, WAL, synchronous FULL и ожидание блокировки 5 секунд.
- Один пользователь может иметь только одно членство в семье. Частичный уникальный индекс разрешает не более одного владельца семьи; создание семьи вместе с владельцем должно быть транзакцией этапа 3.
- Не более одного открытого списка покупок на семью. Создание нового при закрытии — бизнес-транзакция этапа 5.
- Составные foreign keys покупок и желаний запрещают связывать дочернюю запись с родителем другой семьи. Удаление профиля каскадно удаляет желания; подтверждение и права реализуются в API на этапе 8.
- Все семейные таблицы имеют обязательный `family_id`. `users` и `sessions` относятся к пользователю, который может ещё не состоять в семье.
- Владельцы/авторы задач ссылаются на `users`, а не на текущее членство: удаление участника не должно случайно каскадно уничтожить историю. Проверка членства и разрешений на операции — обязанность будущих API. Схема сама не является авторизацией.
- Telegram ID хранится как TEXT. Сессии и приглашения предусматривают хеш токена, а не открытый секрет.
- Временные метки — INTEGER Unix seconds UTC. Даты планирования — календарные `YYYY-MM-DD` в часовом поясе семьи, время — `HH:mm`. Неделя начинается в понедельник, месяц — первого числа.
- `planned_date`/`period_type` отражают актуальный срок, `original_planned_date`/`original_period_type` сохраняют первый. Ручной перенос меняет актуальный срок; автоматическое отображение просрочки не требует обновления строк. История завершения использует `completed_at`.
- Профили вишлистов создаются вручную, обязательной привязки к аккаунту нет. Цена предусматривает целое число минимальных денежных единиц и код валюты; UI и валидация валют появятся на этапе 8.
- Уведомления предусматривают только утреннюю сводку и новое чужое дело. Уникальный ключ получателя/типа/события позволяет учитывать доставку. Планировщик, повторные попытки и обработка неопределённого ответа Telegram ещё не реализованы; одна таблица не гарантирует доставку ровно один раз.
- `updated_at` имеет начальное значение; API при изменении записи обязано обновлять его явно.

Дополнительно есть журнал миграций и временная `prototype_tasks`. Только эту таблицу используют старые открытые endpoints, чтобы промежуточный этап сохранил работоспособность интерфейса без фиктивных семей и nullable-владельцев в настоящих задачах. До первого релиза этапов 1–3 старые endpoints должны получить авторизацию или быть заменены. `prototype_tasks` не является семейной сущностью и не переносится автоматически в `tasks`.

## Резервное копирование и восстановление

Применён SQLite backup API вместо копирования одного активного `.db`: он учитывает зафиксированные страницы WAL. Основание: [better-sqlite3 backup API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#backupdestination-options---promise), [правила foreign keys SQLite](https://www.sqlite.org/foreignkeys.html).

Backup получает уникальное имя, проверяется `integrity_check` и не попадает в Git или Docker build context. Копии в `server-data` переживают пересоздание контейнера, но находятся на том же носителе: сохраняйте отдельную копию вне VPS. Расписание и ротация добавляются в этапе 10.

Для восстановления остановите приложение, сохраните текущую базу и выберите копию. Скопируйте backup под **новым именем**, например `server/data/restored.db`, затем задайте `DATABASE_PATH=data/restored.db`. Не заменяйте открытый файл БД и не смешивайте его с чужими `-wal`/`-shm`. Для Compose измените `DATABASE_PATH` в секции `environment`, поскольку она перекрывает `.env`.

С версией кода, соответствующей копии, выполните `db:migrate` и запустите приложение. Для старой базы прототипа используйте старую версию приложения; новая команда миграции намеренно не принимает её схему. Автотест проверяет восстановление новой схемы из backup и наличие зафиксированных WAL-данных; восстановление на VPS ещё не проверялось.

## Проверки

```sh
npm run lint
npm run build
npm run build --prefix server
npm run typecheck --prefix server
npm test --prefix server
```

Тесты используют временные базы: пустая схема, повторная миграция, откат DDL, неизвестная история, foreign keys, уникальность, даты и периоды, история выполнения, дедупликация, backup с WAL и повторное открытие базы. HTTP-тест создаёт задачу через API прототипа и проверяет её после перезапуска серверного процесса; запросы к AI не выполняются.
